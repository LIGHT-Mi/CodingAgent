# Coding Agent 两分钟演示脚本

## 1. 演示目标

在两分钟内通过一个真实的失败测试修复任务，证明本项目不是对现成 Agent
产品的界面封装，而是自行实现了：

- Agent Loop；
- 上下文管理；
- 模型动作解析；
- 本地文件与命令工具；
- Runtime Policy；
- 多轮会话；
- 可追踪的执行时间线；
- 危险命令的一次性用户批准。

演示的主故事是：

```text
读取项目
→ 运行测试并观察失败
→ 精确修改源码
→ 回读验证文件
→ 再次运行测试并通过
→ 在同一会话中继续追问
→ 展示危险命令批准
```

## 2. 录制前准备

### 2.1 演示 Workspace

使用：

```text
/Users/myx/Documents/GitHub/CodingAgent/examples/coding-agent-demo-workspace
```

该目录必须位于后端 `ALLOWED_WORKSPACE_ROOT` 配置允许的范围内。

演示项目初始缺陷位于：

```text
calculator/operations.py
```

初始实现为：

```python
def multiply(left: int, right: int) -> int:
    """返回两个整数的乘积。"""

    return left + right
```

测试期望 `multiply(3, 4) == 12`，并且包含乘零测试。初始状态下应有两个乘法测试失败。

### 2.2 确认初始失败状态

录制前执行：

```bash
cd examples/coding-agent-demo-workspace
python3 -m unittest discover -s tests -p 'test_*.py'
```

预期结果：

```text
Ran 3 tests
FAILED (failures=2)
```

如果此前排练已经修复源码，在仓库根目录恢复初始版本：

```bash
git restore examples/coding-agent-demo-workspace/calculator/operations.py
```

### 2.3 启动环境

依次确认：

1. PostgreSQL 已启动，数据库已经按最新 Schema 重建。
2. 后端服务已启动。
3. 前端服务已启动。
4. DeepSeek API Key 已通过 `backend/.env` 配置。
5. 前端能够创建 Session 和 Task。
6. 浏览器和终端中不展示 API Key、数据库连接串或 `.env` 内容。

建议提前清空本次演示使用的 Session，或者在前端点击“新建会话”进入空白草稿。

## 3. 两分钟分镜脚本

## 0:00–0:10：建立项目定位

### 画面

打开 Web UI，短暂停留在三栏界面：

- 左侧 Session 会话列表；
- 中间用户与 Agent 对话区；
- 右侧 Agent 执行检查器。

### 口播

> 这是一个没有使用 Agent 框架、由我自行实现 Agent Loop、上下文管理、本地工具和运行策略的编程智能体。

### 展示重点

- 让观众先看到完整产品形态。
- 不在开头讲数据库表、类名或过多实现细节。
- Workspace 输入框显示演示项目路径，但不要展示 `.env`。

## 0:10–1:05：完成真实失败测试修复

### 用户输入

在中间输入框发送：

> 请检查这个项目并运行现有测试，根据失败信息定位并修复问题。修改已有文件前先读取真实源码，优先使用精确编辑；修改后回读文件，并重新运行同一测试命令。最后总结失败原因、修改内容和实际验证结果。

### 预期 Agent 行为

右侧时间线应逐步出现类似流程：

```text
list_files
→ read_file README/source/tests
→ run_command
   exit_code=1
→ edit_file
→ read_file
→ run_command
   exit_code=0
→ FinalAction
```

具体 ToolCall 轮次可能因模型选择略有不同，只要保持以下语义即可：

1. Agent 先读取真实项目内容。
2. 第一次测试失败。
3. Agent 根据失败信息定位 `multiply()`。
4. 使用 `edit_file` 完成唯一精确替换。
5. 修改后再次读取文件。
6. 再次执行相同测试并通过。
7. 最终 Task 状态为 `COMPLETED`。

### 口播

> 模型不能直接访问文件或操作系统，只能提出结构化工具调用，本地 Runtime 校验并执行这些动作。

第一次测试失败时：

> 这里第一次测试的 exit code 是 1，但测试失败只是模型需要分析的 Observation，不等于 Agent Runtime 失败，所以 Agent 会继续定位并修复问题。

出现 `edit_file` 时：

> 文件修改使用 old text 到 new text 的唯一精确替换。找不到或匹配多处都会返回错误，不允许模型猜测修改位置。

第二次测试成功时：

> 修改后 Agent 必须回读文件，并再次运行测试。第二次 exit code 为 0，之后才能给出最终结论。

### 必须拍到的证据

至少清晰展示以下三个画面：

1. 第一次 `run_command` 的 `exit_code=1`，同时 Task 仍处于运行状态。
2. `edit_file` 的精确替换摘要。
3. 第二次 `run_command` 的 `exit_code=0`，最终 Task 为 `COMPLETED`。

### 剪辑建议

- 模型等待时间可以加速或剪掉。
- 重复的文件读取可以快速带过。
- 在两个测试结果和精确编辑结果处恢复正常速度。

## 1:05–1:25：展示同一 Session 的多轮记忆

### 用户输入

Task 0 完成后，在同一 Session 继续发送：

> 请基于上一轮结果，解释为什么这个修改是正确的，并列出实际验证证据；不要继续修改文件。

### 画面

展示：

- 左侧仍然是同一个 Session；
- 中间出现新的用户轮次和 Agent 回答；
- Task 1 与 Task 0 ID 不同；
- 点击 Task 0、Task 1 时，右侧切换到各自独立的执行时间线。

### 口播

> 同一个 Session 下，每一轮用户请求都会创建新的 Task。新任务可以使用历史 Prompt 和最终结论继续对话，但不会把上一轮完整文件内容和命令输出无限塞入上下文。

### 展示重点

说明这是：

```text
一个 Session
└── 多个独立 Task
```

而不是让已经完成的旧 Task 回到 `PENDING` 状态。

## 1:25–1:48：展示危险命令一次性批准

### 用户输入

在同一 Session 继续发送：

> 为了演示一次性命令批准，请执行 `python -c "print('approval-demo')"`。如果需要批准请等待；执行后只根据实际 stdout 告诉我结果。

### 预期行为

当前 `CommandSafetyPolicy` 会将 `python -c` 判断为需要批准，而不是自动执行。

右侧批准面板应展示：

- 完整 argv；
- 规范工作目录；
- 风险等级；
- 命中的安全规则；
- SHA-256 命令指纹；
- 批准有效时间；
- “拒绝执行”和“允许本次执行”按钮。

点击“允许本次执行”，等待 Agent 获得真实 stdout：

```text
approval-demo
```

### 口播

> 模型提出命令不等于命令立即执行。批准绑定当前 Task、ToolCall、完整 argv、工作目录和一次性指纹；批准后仍会重新进行路径和安全校验。

### 展示重点

画面中要同时出现：

```text
完整命令
工作目录
命令指纹
允许本次执行
```

不要只拍批准按钮，否则无法体现一次性批准的约束设计。

## 1:48–2:00：架构总结

### 画面

切换到以下极简架构图，或者将其作为视频覆盖图层：

```text
React Web UI
     ↓
Application Service / TaskRunner
     ↓
ContextManager → LLMGateway → ActionParser
                         ↓
RuntimePolicy ← AgentRuntime → ToolRouter
                                ↓
                   文件工具 / 命令执行 / 用户批准
                                ↓
                         PersistenceService
```

### 口播

> 项目的重点不是封装模型，而是自行实现模型如何观察、行动、纠错、验证和安全终止。

## 4. 视频中应强调的五个设计点

如果实际录制时间有少量浮动，优先保留以下五句话：

1. LLM 只提出动作，本地 Runtime 决定动作能否执行。
2. 测试失败是 Observation，不等于 Agent 失败。
3. 修改成功必须经过回读和命令验证，不能只相信模型描述。
4. 工具请求和对应结果作为完整 Interaction Block 管理。
5. 危险批准绑定完整命令、工作目录和一次性指纹，批准后仍重新校验。

## 5. 不在主视频中展开的能力

以下机制保留到 README 或面试问答，避免两分钟视频信息过载：

- `../`、绝对外部路径和 symlink 逃逸防护；
- stdout/stderr 并发排空与头尾截断；
- 命令超时后的整个进程组终止；
- 子进程最小环境，不继承 API Key 和数据库连接串；
- LLM timeout、rate limit、网络错误和 InvalidAction 重试；
- 最大步数与循环指纹检测；
- Context Sliding Window 和 Context Overflow；
- Fatal ToolCall、Step 和 Task 状态闭合；
- 协作式取消；
- 永久拒绝命令不能通过用户批准执行。

可以在视频结尾或 README 中用一行概括：

```text
路径安全｜命令策略｜有界输出｜上下文预算
状态闭合｜错误重试｜循环检测｜协作式取消
```

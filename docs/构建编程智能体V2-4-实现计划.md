# 构建编程智能体 V2-4 实现计划

最合适的实现方式不是按 F1 → F8 横向逐个模块做完，而是先跑通一条最薄的任务链路，再逐步加入文件工具、命令工具、上下文裁剪和运行策略。这样每一步都有可演示、可测试的功能成果，也能减少后期返工。

## 当前代码基线

目前仓库已经实现的是数据库基础层：

- `Settings` 只从 `backend/.env` 读取 `DATABASE_URL`。
- `settings.DATABASE_URL` 被传给 SQLAlchemy `create_engine()`。
- 已有 `Session → Task → AgentStep/Message → ToolCall` 的 ORM 模型。
- `Task.workspace` 当前只是保存路径字符串，还没有真实 Workspace 校验。
- `Message.sequence` 定义了任务内消息顺序，但还没有分配序号的服务逻辑。
- `ToolCall` 已能保存参数、stdout、stderr、exit code 和结果，但还没有执行或状态流转逻辑。
- `reset_db()` 会先删除全部表再重建。对于当前课程/演示用小原型，这是可接受且更简单的 schema 更新方式。

也就是说，当前完成的是 F8 的“表结构部分”，尚未实现 F1–F7，也没有 F8 的服务层。

## 可以使用的库

根据 `PROJECT_REQUIREMENTS.md`，不能使用 Agent 框架或 Agent SDK，但允许使用模型厂商客户端、OpenAI 兼容网关和原生 Tool Calling。

建议：

- DeepSeek 调用：可使用 `openai` Python 客户端连接 OpenAI 兼容接口，或者使用普通 HTTP 客户端。
- 数据库：继续使用现有 SQLAlchemy；当前小原型不引入 Alembic，schema 变化直接删表重建。
- 配置和参数模型：继续使用 Pydantic / pydantic-settings。
- 测试：引入 pytest。
- 文件工具、Agent Loop、上下文管理、动作解析、终止策略都自行实现，不使用 LangChain、Agents SDK 等框架。

当前仓库还没有提交依赖清单，所以正式开发前要先补 `requirements.txt` 或 `pyproject.toml`，否则现有虚拟环境里的依赖无法被别人可靠复现。

## 第 0 步：先固定核心数据契约

先不要写 Agent Loop，而是确定各模块交换的数据到底是什么。

至少定义：

- `FinalAction`
- `ToolCallsAction`
- `InvalidAction`
- `ToolCallRequest`
- `ToolResult`
- `RuntimeEvent`
- `RuntimeDecision`
- `AgentResult`
- Task、Step、ToolCall 的状态枚举

例如 `ToolResult` 应统一包含：

```text
tool_call_id
tool_name
status
content
error
metadata
```

命令结果的 `exit_code/stdout/stderr` 放在 metadata 或命令专用结果对象中。

这一层应是普通 Python 数据结构，不依赖数据库 ORM。后面 F3、F4、F5、F6、F7 都围绕这些结构工作，避免每层使用不同字典格式。

验收标准：能用单元测试构造所有正常、错误和终止结果，不调用数据库和模型。

## 第 1 步：把现有数据库模型包成 F8 持久化服务

不要让未来的 F1、F2、F6 到处直接操作 SQLAlchemy Session。

先实现最小持久化接口：

- 创建/查询 Session
- 创建 Task
- Task：`PENDING → RUNNING → 终态`
- 创建和结束 AgentStep
- 保存 Assistant Message
- 保存 ToolCall
- 更新 ToolCall 执行结果
- 保存 Tool Result Message
- 按 `sequence` 查询任务历史

这一阶段还需要解决几个表结构问题：

1. 增加模型供应商返回的 Tool Call ID

   原生 Tool Calling 的结果消息需要引用供应商 Tool Call ID。现在 `ToolCall.id` 是本地 UUID，不能保证能正确重建下一轮模型上下文。建议增加 `provider_call_id`。

2. 明确 Message 序号分配

   统一由持久化服务分配，不能由多个调用方自己计算。

3. 原型阶段继续使用删表重建

   当前是课程/演示用的小原型，没有线上历史数据和平滑迁移需求。schema 发生变化时继续使用 `reset_db()` 删除并重建表，不引入 Alembic，也不维护迁移文件。等未来出现需要保留的数据或部署环境后，再单独评估迁移机制。

4. 状态值集中定义

   当前模型存的是普通字符串。至少应使用统一枚举或常量并在服务层验证状态流转。

验收标准：不用 LLM，也能完整保存一条 Task、Step、Assistant Message、ToolCall、Tool Result，并按原顺序读取。

## 第 2 步：实现 F3，但先只验证模型动作解析

→ 调用客户端

→ 解析 Final / Tool Calls / Invalid

不要让 F3 调用工具，也不要在 F3 写数据库。

这一阶段应同时实现 Tool Schema Registry，因为模型生成什么参数取决于暴露给它的 schema。

1. 第 2.1 步：定义 LLM 请求与标准化响应契约。
2. 第 2.2 步：定义 Tool Schema Registry。
3. 第 2.3 步：实现 DeepSeek 响应标准化。
4. 第 2.4 步：实现 FinalAction、ToolCallsAction、InvalidAction 解析。
5. 第 2.5 步：使用固定响应完成离线单元测试。
6. 第 2.6 步：实现真实 DeepSeek API 连接。
7. 第 2.7 步：执行少量在线 smoke test。

测试重点：

- 只有最终文本 → `FinalAction`
- 一个 Tool Call → `ToolCallsAction`
- 多个 Tool Call → 保持原始顺序
- arguments 不是合法 JSON → `InvalidAction`
- 未知响应结构 → `InvalidAction`
- timeout/rate limit/network error → 对应 `RuntimeEvent`

验收标准：给定固定的模拟模型响应，能稳定得到标准化 `AgentAction`。

## 第 5 步：加入文件修改能力

按风险从低到高增加：

1. `create_file`
2. `write_file`
3. `edit_file`
4. `delete_file` 最后再决定是否实现

建议明确语义：

- `create_file`：目标已存在则返回错误，不覆盖。
- `write_file`：明确表示整体覆盖已有文件。
- `edit_file`：使用精确的 `old_text → new_text` 替换；找不到或匹配多处时返回错误，不猜测。

验收标准：Agent 能读取一个文件、精确修改、再次读取确认内容。

## 第 6 步：加入命令执行，完成编程任务闭环

本步只在现有文件工具和基础 Agent Loop 上增加一个 `run_command`。命令执行使用 Python 标准库 `subprocess` 及相关进程 API 本地实现，不引入 Agent 框架、托管代码执行服务或第三方 Shell 封装。

### 6.1 固定 `run_command` 契约

定义普通 Python 数据结构：

```text
RunCommandArguments
├── command: tuple[str, ...]
└── cwd: str = "."
```

- `command` 必须是非空字符串数组，每个元素对应一个 argv，不接收整条 Shell 字符串。
- `cwd` 是 Task Workspace 内的相对目录，默认为 `"."`。
- 不允许模型传入环境变量、超时时间、Shell 开关或后台执行选项。
- 始终使用 `shell=False`，不解析管道、重定向、`&&`、`;` 或命令替换。
- 继续使用现有 `ToolResult` 作为文件与命令工具的统一结果，不增加 ORM 专用契约。

### 6.2 增加命令资源保护配置

由应用装配层提供固定配置，建议初始值：

```text
COMMAND_TIMEOUT_SECONDS=30
MAX_COMMAND_OUTPUT_BYTES_PER_STREAM=65536
COMMAND_TERMINATION_GRACE_SECONDS=2
```

这些限制保护本地命令执行，不属于第 7 步的模型上下文预算。

### 6.3 实现 `WorkingDirectoryGuard`

命令工作目录校验与文件路径校验职责不同，应新增独立 Guard：

1. 校验已保存的 Task Workspace 仍是规范绝对目录。
2. 相对 `cwd` 以 Task Workspace 为基准解析。
3. `resolve()` 符号链接和 `..`。
4. 目标必须存在且是目录。
5. 真实目录必须位于 Task Workspace 内。

`cwd` 越界返回 `REJECTED ToolResult`；路径缺失或类型错误返回普通 `ERROR ToolResult`。

### 6.4 实现结构化 `CommandSafetyPolicy`

安全策略只做判断，不直接执行命令。统一返回 `CommandSafetyDecision`：

```text
verdict: ALLOW | REJECT
reason
rule_id
risk_level
approval_eligible
```

- 普通测试、构建和项目运行命令可以自动执行。
- 高风险可执行程序、Shell 解释器和明显的 Shell 操作符必须被识别。
- 未来可能经用户明确批准后执行的命令，设置 `approval_eligible=true`。
- 即使用户批准也不应由当前本地执行器运行的命令，设置 `approval_eligible=false`。
- 初版优先使用支持验收任务的小型可执行程序允许集，不尝试穷举并解析所有 Shell 语义。
- 策略拒绝是模型可见的普通 Observation，不使 Task 失败。
- 对 `approval_eligible=true` 的拒绝结果，在 metadata 中记录 `rule_id`、`risk_level`、规范化 argv、规范工作目录和稳定的 `command_fingerprint`，供计划末尾的用户批准步骤使用。
- 第 6 步中所有 `REJECT` 都直接生成 `REJECTED ToolResult`，不询问用户、不暂停 Task，也不执行命令。

### 6.5 实现受控子进程环境

子进程不应默认继承包含 `DEEPSEEK_API_KEY` 和 `DATABASE_URL` 的完整服务进程环境。执行器只构造运行测试和构建所需的最小环境，例如 `PATH`、locale 和临时目录；不允许模型追加或覆盖环境变量。

### 6.6 实现有界的输出收集

`ProcessOutputCollector` 应在进程运行期间同时持续读取 stdout 和 stderr，避免管道填满导致子进程阻塞：

- 限制内存中保留的输出字节数，并同时保留开头和结尾。
- 记录原始字节数、截断标记和丢弃字节数。
- 使用 UTF-8 `errors="replace"` 构造模型可见文本，非 UTF-8 输出不使 Runtime 崩溃。
- 截断后在结果文本中明确标注，不能让模型误以为看到了全部输出。

### 6.7 实现 `CommandExecutor`

使用标准库 `subprocess.Popen` 执行：

- `shell=False`。
- `stdin=DEVNULL`，不允许命令占用 Agent 的交互输入。
- stdout/stderr 分别使用 PIPE。
- 子进程创建独立进程组或 session。
- 使用单调时钟计算 timeout。
- 超时先终止整个进程组；宽限期后仍未退出则强制终止；最后排空 stdout/stderr。

当前原型以 POSIX/macOS/Linux 为执行环境；Windows Job Object 和容器执行不在本步范围。

### 6.8 统一命令结果语义

必须保持设计文档中的重要语义：

```text
pytest 失败、编译失败、exit_code != 0
都是模型需要看到的 Observation，
不等于 Agent Runtime 失败。
```

结果映射：

- 进程正常结束：无论 `exit_code` 是否为 0，都返回 `COMPLETED ToolResult`。
- 超时且已完成进程组清理：返回 `TIMEOUT ToolResult`。
- 参数错误、目录缺失或进程创建失败：返回普通 `ERROR ToolResult`。
- 安全策略拒绝或工作目录越界：返回 `REJECTED ToolResult`。
- 只有执行层不可恢复的内部异常才作为 Fatal Tool Error 交给 Runtime，并闭合所有 ToolCall 状态。

`ToolResult.content` 必须包含命令、工作目录、结束状态、exit code、stdout、stderr 和截断标记，因为当前 ContextManager 只把 Tool Result Message 内容重新发给模型。

`metadata` 记录规范化 argv、规范工作目录、`exit_code/stdout/stderr`、timeout、运行时长、输出字节数、截断标记和终止信号。现有持久化服务继续从 metadata 写入 ToolCall 的命令结果字段。

### 6.9 将执行工具路由泛化为文件与命令工具路由

当前 `FileToolRegistry` 和 `PreparedToolCall` 只接受文件工具。本步应直接更新为通用本地工具概念并修改全部调用方，不保留旧名称兼容接口：

- 模型 `ToolSchemaRegistry` 仍只保存 JSON Schema。
- 本地执行注册表同时保存六个文件工具和 `run_command` 执行器。
- `ToolRouter.prepare()` 负责工具查找、严格参数校验、路径/工作目录校验和安全决策。
- `ToolRouter.execute()` 只接收已准备的文件或命令调用。
- `AgentRuntime` 保持现有两阶段状态流：准备失败时 `PENDING → ERROR/REJECTED`；开始真实执行后 `PENDING → RUNNING → COMPLETED/ERROR/TIMEOUT`。

Runtime 不导入 `subprocess`、不解析命令，也不根据 exit code 决定 Task 成败。

### 6.10 注册 Schema 并更新模型提示词

新增严格 `run_command` JSON Schema：

- `type=object`。
- `command` 是至少包含一个非空字符串的数组，必填。
- `cwd` 是非空字符串，默认 `"."`。
- `additionalProperties=false`。

模型最终看到七个工具：

```text
list_files
read_file
search_files
create_file
write_file
edit_file
run_command
```

System Prompt 只增加当前必要规则：可用 `run_command` 执行测试、构建和项目运行；非零 exit code、timeout 和拒绝结果都是需要分析的 Observation；修改后应运行相关验证；不得声称未实际执行的命令成功。当前仍不暴露 `delete_file`。

### 6.11 更新装配入口

更新模型网关工厂、CLI 和 `app.tools` 导出：

- 模型网关使用七个工具 Schema。
- CLI 装配通用本地工具注册表、命令安全策略、工作目录 Guard、命令执行器和资源上限。
- `TaskService`、LLM Gateway 调用方式和持久化 Schema 不变。

本步不需要 Alembic；现有 ToolCall 字段和 `save_tool_result()` 已能保存 stdout、stderr、exit code 和 metadata。

### 6.12 离线验收

所有模型响应使用模拟数据，不消耗 API 额度。至少覆盖：

- `run_command` 参数缺失、类型错误、空 argv 和未知参数。
- 合法 `cwd`、缺失目录、文件路径、`..` 越界、绝对外部路径和符号链接逃逸。
- 允许命令、必须拒绝命令、将来可申请批准命令，以及其结构化决策和稳定指纹。
- 安全策略拒绝后没有创建子进程。
- exit code 0 和非 0 都映射为 `COMPLETED`，stdout/stderr/exit code 进入结果和持久化字段。
- 输出上限保留头尾、标注截断，且大量输出不会造成死锁。
- 非 UTF-8 stdout/stderr 能生成普通结果。
- timeout 返回 `TIMEOUT`，父子进程均被终止，不遗留运行中进程。
- 子进程不能读取 API Key 和数据库连接字符串。
- 参数、目录、策略拒绝、非零 exit code 和 timeout 均持久化为 Tool Result Observation，Task 继续下一轮。
- Fatal Tool 异常仍闭合当前 Step 的所有 ToolCall，不留下 `PENDING/RUNNING`。
- 回归现有文件工具、历史恢复、Agent Loop、Task 生命周期和 CLI 测试。

纵向离线用例：

```text
列出并读取缺陷项目
→ run_command 执行测试，exit_code != 0 但 ToolResult=COMPLETED
→ 模型读取失败 Observation
→ edit_file 精确修改
→ read_file 验证文件
→ run_command 再次测试，exit_code=0
→ FinalAction
```

### 6.13 在线验收

准备一个带失败测试的小项目，要求 Agent 检查项目、运行测试、根据失败修改代码并再次测试。最终验证：

- Agent 至少执行两次 `run_command`，先看到失败，再看到成功。
- 失败测试不使 Task 失败，Agent 能根据 stdout/stderr 继续修复。
- 文件修改经过读取、精确编辑和再次读取验证。
- Task 最终为 `COMPLETED`，命令 ToolCall 与 TOOL_RESULT Message 一一对应。
- 被安全策略拒绝的命令不创建子进程，且模型能看到拒绝原因。

需要特别注意：校验 `cwd` 位于 Workspace 内，不等于命令只能访问 Workspace。命令仍可能使用绝对路径访问外部文件，被执行的 Python 代码和测试代码也具有当前用户的本地权限。因此 MVP 应诚实定义为“受策略限制的本地命令执行”，不能描述成严格沙箱。真正的文件系统、网络、进程和资源隔离需要后续增加容器或操作系统级沙箱。

本步明确不实现：

- 第 7 步的上下文预算、历史裁剪和摘要。
- 第 8 步的 LLM 重试、backoff、循环指纹、取消和正式 Runtime Policy。
- 完整用户批准工作流及其数据库状态、暂停/恢复 API、CLI 询问或前端交互；这些内容统一放到计划末尾的第 11 步。
- 容器或操作系统级沙箱、网络隔离和跨平台进程树管理。
- Shell 字符串、管道、重定向、后台进程和模型自定义环境变量。
- `delete_file`。

这一步完成后，已经满足官方核心要求，可以作为第一个可提交版本。

## 第 7 步：把简单历史升级为正式 F2 Context Manager

前面可以先把全部历史放进模型；闭环稳定后再实现文档中的上下文策略：

1. System Prompt 永远保留。
2. Original Task 永远保留。
3. Assistant Tool Call 与对应 Tool Result 组成不可拆分的 Interaction Block。
4. 先截断过长的 Tool Result。
5. 再按 Block 删除最旧历史。
6. 仍超预算则返回 `ContextOverflowEvent`。

MVP 先使用字符预算，暂时不做 LLM 摘要，也不判断“语义重要性”。

Tool Result 截断建议保留：

- 开头
- 结尾
- 原始长度
- 明确的截断标记

因为编译错误经常在末尾，只保留开头会损失关键信息。

验收标准：构造大量历史后，Context 不超过预算，并且不会留下没有对应结果的 Tool Call。

## 第 8 步：实现正式 F7 Runtime Policy

等正常闭环稳定后，再集中处理异常和终止规则：

- LLM timeout/rate limit/临时网络错误：可重试。
- InvalidAction：可重试。
- Context overflow：直接失败。
- Fatal Tool/System/Database error：直接失败。
- 普通 Tool Error：作为 Observation 继续。
- 最大步数：`TERMINATED/MAX_STEPS`。
- 用户中断：`CANCELLED`。
- 循环检测：最后加入。

重试需要明确：

- 重试的是当前 LLM 调用。
- 不创建新的 AgentStep。
- 不重复保存 Assistant Message。
- 成功进入下一轮后清零当前重试计数。

循环检测不要依赖 LLM 判断。可以对最近几轮的：

```text
tool_name + 标准化 arguments + 结果摘要
```

计算指纹，连续重复达到阈值后终止。

验收标准：分别模拟网络超时、无效响应、工具错误、最大步数和循环调用，验证 Task/Step 状态完全符合设计。

## 第 9 步：建立面向前端的应用服务与 Web API 边界

项目将 Web UI 作为自定义必做功能。第 9 步先让已经稳定的 Agent 核心可以被 CLI 和前端共同调用，不在本步编写正式前端页面。

Web API 可以使用 FastAPI 这类普通 Web 框架。Web 框架只负责 HTTP 输入输出，不代替 Agent Loop、Context Manager、Tool Router、Runtime Policy 或本地工具执行，因此不违反项目对 Agent 框架 / SDK 的限制。实施时再根据当前依赖方式正式确认并添加 Web 依赖。

本步需要完成：

1. 抽取统一应用装配入口，集中创建 `PersistenceService`、`ContextManager`、`LLMGateway`、`ToolRouter`、`RuntimePolicy`、`AgentRuntime` 和 `TaskService`。CLI 与 Web API 必须复用同一套装配，不各自维护 Agent 配置。
2. 将“创建 Task”与“执行 Task”拆成明确的应用服务边界。提交任务后应先返回 `task_id`，不让创建请求一直阻塞到 Agent 完成。
3. 增加最小 Web API，支持创建任务、查询 Task 状态和最终结果、查询 Step / Message / ToolCall 历史，以及请求取消正在运行的 Task。
4. 为 Task 提供后台执行边界。后台任务使用自己的数据库 Session，不复用已经结束的 HTTP 请求 Session。
5. 增加运行中 Task 的取消令牌注册与释放机制，使取消 API 能调用第 8 步已实现的 `CancellationToken`。当前原型可以先使用单进程内存注册表，但必须明确它不支持服务重启后恢复或多进程共享。
6. 定义面向客户端的请求/响应数据结构，不直接暴露 ORM 对象，不向前端返回 API Key、数据库连接串或其他服务端敏感配置。
7. 保留薄 CLI，让它复用统一应用服务；将 Ctrl+C 转换为 `CancellationToken.cancel()`，而不是直接绕过 Runtime 中止进程。

前端在第 10 步先通过轮询获取进度。本步不提前实现 WebSocket、SSE、跨进程任务队列、暂停/恢复、多用户权限或危险命令批准工作流。

验收标准：

- 创建任务的 HTTP 请求能快速返回 `task_id`，Agent 在后台继续运行。
- 能通过 API 查询 `PENDING/RUNNING` 和各类终态，并还原 Step、Message 和 ToolCall 顺序。
- 取消请求能到达对应 `CancellationToken`，最终使 Task 进入 `CANCELLED`，不遗留可正常写入数据库的 `RUNNING` Step/ToolCall。
- CLI 和 Web API 使用相同的 Agent 配置和应用服务。
- Web API 全部使用模拟 Gateway 完成离线测试，不消耗模型额度。

## 第 10 步：实现并接入正式前端

第 9 步 Web API 稳定后，再建立独立前端工程并通过 HTTP API 接入 Agent。前端不直接访问数据库，不复制 Agent Runtime 状态机，服务端 Task 状态是唯一事实来源。

本步需要完成：

1. 根据当时仓库和演示环境确定前端技术栈，建立独立的前端目录、启动命令和环境配置，不将后端 API Key 写入前端环境或打包产物。
2. 实现任务提交界面，要求用户输入任务描述和 Workspace，提交后保存服务端返回的 `task_id`。
3. 实现任务运行视图，展示 Task 状态、Step 编号、Assistant 工具请求、ToolCall 状态、Tool Result 摘要和最终答案/错误/终止原因。
4. 使用轮询同步运行进度，在 Task 进入终态后停止轮询，并正确处理请求失败、页面刷新和任务不存在。
5. 实现取消按钮，只有未进入终态的 Task 可以取消；取消后继续轮询，直到服务端确认 `CANCELLED` 或返回明确错误。
6. 保持页面展示与数据库顺序一致：Step 按 `step_number`，Message 按 `sequence`，ToolCall 按 Step 和 `call_index` 排列。
7. 补齐前后端联调配置、运行说明和最小界面测试，确保新人可以按文档启动数据库、后端和前端。

本步不实现在线文件编辑器、Git diff 回滚、任务恢复、多用户鉴权、WebSocket/SSE 流式传输或危险命令批准页面。这些不影响前端展示当前稳定的 Agent 闭环。

验收标准：

- 用户可以在前端创建任务，页面立即获得 `task_id`。
- 前端能按稳定顺序展示 Agent 的多轮过程，包括工具请求、工具结果和最终答案。
- 用户取消后，界面最终显示 `CANCELLED`，服务端不遗留可正常写入数据库的运行中状态。
- 前端不包含 `DEEPSEEK_API_KEY`、`DATABASE_URL` 或其他服务端秘密。
- 使用一个带失败测试的小项目完成前后端纵向验收：

```text
给 Agent 一个包含缺陷和失败测试的小项目
→ Agent 列目录
→ 读取代码和测试
→ 运行测试
→ 根据错误修改代码
→ 再次运行测试
→ 测试通过
→ 输出总结
```

这条任务能在两分钟视频里展示读文件、写文件、命令执行、多轮处理、错误观察和最终终止，覆盖度最高。

## 第 11 步：实现危险命令的用户询问与批准工作流

第 6～10 步完成后，按照真实数据流落实如下实现：

1. `CommandSafetyPolicy` 使用 `ALLOW / REQUIRE_APPROVAL / REJECT` 三种互斥决策。永久拒绝规则不能由用户批准覆盖。
2. 新增一次性 `CommandApprovalRequest` 持久化记录，绑定 Task、Step 和 ToolCall，并保存完整 argv、规范工作目录、指纹、规则、风险、原因和有效期。状态为 `PENDING / APPROVED / REJECTED / EXPIRED / INVALIDATED / CONSUMED / CANCELLED`。
3. 等待批准时 Task 和 Step 保持 `RUNNING`，ToolCall 保持 `PENDING`，不增加平行的 Task 等待状态。批准请求是唯一表达等待与审计事实的对象。
4. `CommandApprovalService` 负责创建、等待、决定、失效和一次性消费；`CommandApprovalCoordinator` 只负责当前单进程内唤醒。交互逻辑不进入命令执行器。
5. 用户允许后，`ToolRouter` 使用原始结构化参数重新校验工作目录、命令指纹和当前安全策略。只有校验通过并原子消费批准请求后，ToolCall 才进入 `RUNNING` 并创建子进程。
6. 用户拒绝、请求过期、任务取消或重新校验失败都不创建子进程，保存明确的 `REJECTED ToolResult`，完成当前 Step 后由 Agent 下一轮处理 Observation。
7. Web API 提供批准请求查询和决定接口；Task Snapshot 同时返回批准记录。决定请求只接受决定和展示指纹，不接受 argv 或 cwd。
8. 右侧 Agent 检查器展示精确 argv、规范工作目录、风险等级、安全规则和指纹，并提供“允许本次执行 / 拒绝执行”。前端决定后继续使用原有统一快照轮询。

验收覆盖：批准前无子进程；精确批准后只执行一次；拒绝、过期、指纹篡改和永久拒绝均不执行；ToolCall 与 ToolResult 生命周期闭合；API 与前端不允许替换命令参数。

当前边界：批准协调器是单进程内存对象，数据库是审计事实来源；不支持服务重启后恢复等待、多进程共享、远程任务队列或跨进程暂停/恢复。CLI 仍复用同一应用服务边界，但当前正式交互入口是 Web API 与前端；以后接入 CLI 询问不需要修改 `CommandExecutor`。

## 不建议完全照图拆成大量类

设计文档里的 `ResultAssembler`、`StepController`、`ActionRouter`、`ToolResultBuilder` 等更像职责说明，不意味着现在都应该成为独立类。

初期建议保持少量清晰模块：

```text
agent/
  contracts.py
  runtime.py
  context.py
  policy.py

llm/
  gateway.py
  deepseek.py
  schemas.py

tools/
  registry.py
  path_guard.py
  file_tools.py
  command_tool.py

db/
  models/
  repositories.py
  persistence.py

api/
  task_service.py

cli.py
```

当某个文件职责明显变多时再拆分。这样既保留 F1–F8 的职责边界，又不会在功能尚未运行前产生大量空壳类。

最关键的里程碑是第 6 步：完成它就得到一个真正可工作的 Coding Agent；第 7、8 步在这个闭环上提升稳定性与可解释性；第 9 步建立面向多交互入口的应用服务和 Web API；第 10 步完成正式前端与真实演示；第 11 步在这些稳定边界上加入可等待、可审计的一次性用户命令批准能力。

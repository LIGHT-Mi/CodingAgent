# 构建编程智能体项目需求文档

本文档基于《推免考核题目学生版.pdf》以及当前对话中已讨论的 Coding Agent 设计思路整理。

重要区分：

- **题目硬性要求**：来自官方 PDF，必须满足。
- **建议性设计**：来自当前项目讨论，用于指导实现，不属于官方强制要求。

## 1. 项目目标

### 1.1 题目硬性要求

需要个人独立设计并实现一个 **编程智能体（coding agent）**。

该 agent 需要通过与大语言模型交互，能够自主完成编程任务，至少应具备以下能力：

- 读文件；
- 写文件；
- 执行命令；
- 根据用户交给它的编程任务进行多步处理。

官方题目给出的类比对象包括简化版的 Claude Code、Codex、OpenCode、DeepSeek Harness 等。

### 1.2 功能复杂度要求

题目没有强制要求实现复杂功能。

官方明确说明：功能繁简不限，可以很简单，也可以做得完善。因此，项目重点不是功能数量，而是需要真正自行实现一个能运转的 coding agent，并能解释其运行机制。

## 2. 官方硬性限制

### 2.1 禁止封装现成 Agent 产品

不得在现成 agent 产品上简单封装界面。

也就是说，项目不能只是给 Claude Code、Codex、OpenCode、DeepSeek Harness 或类似产品套一层 UI 或命令行入口。

### 2.2 禁止使用 Agent 框架或 Agent SDK

不得使用任何 agent 框架 / SDK。

官方举例包括但不限于：

- LangChain；
- LlamaIndex；
- OpenAI Agents SDK；
- Claude Agent SDK；
- AutoGen；
- CrewAI。

如果某个库本质上替项目完成了 agent loop、工具编排、任务规划、上下文管理等核心 agent 逻辑，应视为不符合题目精神，应避免使用。

### 2.3 允许使用的能力

官方允许使用：

- 模型厂商的 API 客户端库；
- OpenAI 兼容网关；
- 模型原生的 tool calling 接口。

这些能力可以用于调用模型，但不能替代项目自身的 agent 核心实现。

### 2.4 禁止依赖服务端托管的代码执行或文件工具

不得依赖 API 服务端托管的代码执行或文件工具。

官方举例包括：

- Code Interpreter；
- Files API。

项目中的文件读写、命令执行、工具调用等能力应由本地程序自行实现。

### 2.5 重要逻辑必须自行编写

官方明确要求重要逻辑需要自行编写，包括但不限于：

- 对话历史与上下文管理；
- 工具的定义与本地执行；
- 模型输出的解析；
- 循环终止条件；
- 错误处理。

这些部分应作为项目的核心实现内容，不能交给现成 agent 框架代劳。

## 3. 开发与安全规则

### 3.1 截止时间

截止时间为：

**2026 年 9 月 2 日 24:00（北京时间，即 2026 年 9 月 3 日 0 点）**

截止时间后请勿再向提交用 Git 仓库推送新提交。

### 3.2 AI 工具使用

允许并鼓励使用任何 AI 工具辅助开发。

但需要注意：开发者本人必须对项目中的每一处设计负责，面试时需要能解释 agent 为什么这样运转，并能为设计决策给出理由。

### 3.3 模型与编程语言

官方不限制：

- agent 运行时调用的模型；
- 项目使用的编程语言。

因此可以根据个人熟悉程度选择 Python、TypeScript、Go、Java 等语言，也可以选择任意可用的大模型 API。

### 3.4 凭据安全

API key 等凭据必须通过以下方式提供：

- 环境变量；
- 未入库的本地配置文件。

凭据不得出现在：

- Git 仓库；
- `README.txt`；
- 演示视频。

如果曾经误提交凭据，需要立即作废并更换。

## 4. 提交物要求

官方要求提交物共三项，但最终提交内容是一个 zip 文件。

### 4.1 Git 仓库

要求：

- 必须是题目发布后新建的公开仓库；
- GitHub、Gitee 均可；
- 保留完整提交历史；
- 不得压缩或改写已推送的历史；
- 截止时间后不要再向仓库推送新提交；
- 仓库地址需要写在提交的 `README.txt` 中。

评委会结合提交时间与提交内容了解开发过程，因此提交历史本身也是评审参考材料。

### 4.2 README.txt

要求：

- 文件名为 `README.txt`；
- 1000 汉字以内；
- 需要包含 Git 仓库地址；
- 需要说明如何运行项目；
- 需要说明特色功能；
- 可以补充其它想说明的内容。

注意：这是最终提交压缩包中的 `README.txt`，不等同于仓库内可以更详细展开的 `README.md`。仓库内可以另外维护详细文档，但最终提交的 `README.txt` 必须控制在 1000 汉字以内。

### 4.3 演示视频

要求：

- 时长 2 分钟以内；
- mp4 格式；
- 文件大小不超过 200 MB；
- 演示 agent 完成一个真实编程任务的过程；
- 简要讲解功能实现；
- 允许剪辑；
- 允许加速播放。

视频中不得出现 API key 等凭据。

### 4.4 最终压缩包

最终提交内容仅包含一个 zip 文件。

要求：

- zip 文件用本人姓名命名；
- zip 内包含 `README.txt` 和视频文件；
- 提交至官方表单；
- 可重复提交，以最后一次为准。

官方提交表单：

https://table.nju.edu.cn/dtable/forms/283d6c7d-475a-4f41-8baf-d3f45966ef2d/

## 5. 面试环节要求

### 5.1 面试流程

面试环节会现场播放演示视频。

之后需要：

- 简单介绍自己的设计方案；
- 回答评委提问。

### 5.2 提问重点

评委提问重点关注：

- 是否理解 agent 为什么这样运转；
- 是否能为自己的设计决策给出辩护。

因此，项目实现时应避免只追求“跑起来”，还需要保留清晰的设计说明，确保自己能解释每个核心模块的职责和数据流。

## 6. 建议性项目设计

本节内容属于当前对话中讨论出的实现建议，不是官方硬性要求。

### 6.1 推荐仓库名

当前讨论中推荐的仓库名为：

**`code-agent-lab`**

理由：

- 能直接表达项目主题是 coding agent；
- `lab` 适合课程项目和实验型项目；
- 名称简短，适合作为 GitHub 仓库名；
- 不把实现方式绑定死，后续扩展 session、task、agent step、tool calling、context management 等机制都比较自然。

可选名称还包括：

- `dev-agent`；
- `coding-agent`；
- `autocode-agent`；
- `agentic-coder`；
- `codeforge-agent`。

### 6.2 推荐核心模块

为满足题目中“重要逻辑自行编写”的要求，建议至少拆出以下核心模块。

这些模块不是官方指定名称，但对应官方要求中的关键能力。

#### 6.2.1 Agent Loop

负责驱动 agent 的主循环：

- 接收用户任务；
- 构造发送给模型的上下文；
- 调用模型；
- 解析模型回复；
- 判断是执行工具、继续思考，还是结束任务；
- 在达到终止条件后输出最终结果。

该模块对应官方要求中的模型交互、循环终止条件、错误处理等内容。

#### 6.2.2 Message / Conversation History

负责保存对话历史和模型交互记录。

建议记录：

- 用户输入；
- agent 发给模型的消息；
- 模型返回内容；
- 工具调用请求；
- 工具执行结果；
- 最终回答。

该模块对应官方要求中的对话历史与上下文管理。

#### 6.2.3 Context Management

负责决定每一轮模型调用时放入哪些上下文。

可以包括：

- 最近对话消息；
- 当前任务状态；
- 工具执行结果摘要；
- 已读取文件的内容或摘要；
- 当前工作目录信息；
- 错误信息。

如果项目较简单，可以先使用固定窗口的上下文管理；如果时间允许，再扩展摘要、裁剪或优先级策略。

#### 6.2.4 Tool Definition

负责定义 agent 可以调用哪些本地工具。

建议至少包含：

- 读取文件；
- 写入文件；
- 列出目录；
- 搜索文件或文本；
- 执行命令。

工具定义中应明确：

- 工具名称；
- 参数结构；
- 功能说明；
- 返回结果格式；
- 失败时的错误信息。

该模块对应官方要求中的工具定义。

#### 6.2.5 Local Tool Execution

负责真正执行本地工具。

需要注意：

- 文件操作应限制在项目工作目录或明确允许的目录内；
- 命令执行应记录 stdout、stderr、退出码；
- 写文件前应避免误覆盖无关文件；
- 出错时返回清晰错误，而不是让程序直接崩溃。

该模块对应官方要求中的本地执行和错误处理。

#### 6.2.6 Model Output Parsing

负责从模型回复中解析出下一步动作。

如果使用模型原生 tool calling，可以解析模型返回的 tool call 结构。

如果不使用原生 tool calling，也可以自定义 JSON 格式，例如让模型输出：

```json
{
  "action": "read_file",
  "args": {
    "path": "src/main.py"
  }
}
```

无论采用哪种方式，都应处理解析失败、参数缺失、工具不存在等情况。

该模块对应官方要求中的模型输出解析。

#### 6.2.7 Task / AgentStep

建议引入任务和步骤记录，用于解释 agent 的运行过程。

`Task` 可以表示用户交给 agent 的一次完整编程任务。

`AgentStep` 可以表示 agent 在任务中的一次动作，例如：

- 模型思考；
- 读取文件；
- 修改文件；
- 执行测试；
- 根据错误继续修复；
- 输出最终结果。

这不是官方强制要求，但有助于：

- 让运行过程可追踪；
- 生成演示视频时更容易讲解；
- 面试时解释 agent 的决策链路；
- 后续扩展日志、数据库或可视化界面。

#### 6.2.8 Session

建议使用 `Session` 表示一次连续交互上下文。

它可以关联多个用户任务，也可以只关联一次任务。是否实现持久化数据库不是官方硬性要求，需要根据开发时间决定。

### 6.3 推荐最小可行版本

为了优先满足题目要求，建议最小可行版本包含：

- 命令行入口；
- 用户输入一个编程任务；
- agent 调用大模型生成下一步动作；
- 本地实现文件读取工具；
- 本地实现文件写入工具；
- 本地实现命令执行工具；
- agent 能根据工具结果继续调用模型；
- agent 有明确终止条件；
- agent 能输出最终结果；
- 运行日志能够展示 agent 每一步做了什么。

这个版本已经覆盖官方关键要求，不需要一开始就实现复杂 UI、数据库、插件市场或多 agent 协作。

### 6.4 可选增强功能

以下内容可以提升项目完整度，但不是官方硬性要求：

- Web UI 或 TUI；
- 更漂亮的运行日志；
- 会话持久化；
- SQLite 数据库存储 session、task、message、agent step；
- 文件修改 diff 展示；
- 命令执行前确认机制；
- 工作目录沙箱限制；
- 长上下文摘要；
- 自动测试与失败重试；
- 支持多种模型配置；
- 支持自定义工具；
- 任务执行报告生成。

实现这些功能时，应优先保证核心 agent 逻辑清晰可解释，而不是堆叠功能。

- [ ] 没有依赖 Code Interpreter、Files API 等服务端托管代码执行或文件工具。
- [ ] 文件读写由本地程序自行实现。
- [ ] 命令执行由本地程序自行实现。
- [ ] 对话历史与上下文管理由项目自行实现。
- [ ] 工具定义与本地执行由项目自行实现。
- [ ] 模型输出解析由项目自行实现。
- [ ] 循环终止条件由项目自行实现。

- [ ] `README.txt` 控制在 1000 汉字以内。

## 8. 实现优先级建议

建议按以下顺序推进：

1. 搭建最小命令行入口。
2. 接入模型 API 客户端。
3. 设计模型输出动作格式。
4. 实现本地工具：读文件、写文件、执行命令。
5. 实现 agent loop。
6. 加入对话历史和上下文管理。
7. 加入错误处理和终止条件。
8. 用一个真实小任务验证 agent 能闭环完成。
9. 整理仓库 README 和演示脚本。
10. 录制 2 分钟以内演示视频。
11. 编写最终提交用 `README.txt`。
12. 打包并提交。

## 9. 不应误判为官方要求的内容

以下内容可以做，但官方 PDF 没有强制要求：

- 必须使用某一种编程语言；
- 必须使用某一个大模型；
- 必须实现 Web UI；
- 必须实现数据库；
- 必须实现多 agent；
- 必须实现复杂任务规划器；
- 必须实现长期记忆；
- 必须实现插件系统；
- 必须支持远程沙箱；
- 必须达到 Claude Code 或 Codex 的完整能力。

这些内容只能作为项目增强点，不能写成官方硬性要求。
